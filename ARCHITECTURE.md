# Deepwater architecture and product definition

Deepwater is one product family with distinct applications: Echo for language
learning, Amber for mutual connection and dating, and AI fashion as a future
product. The visual identity is supplied by the owner; this document defines
product boundaries and system behavior, not a logo redesign.

Start here:

- [Materials-based product, algorithm, acceptance, architecture, and roadmap](docs/product/DEEPWATER_MATERIALS_BASED_PROPOSAL.md)
- [Product scope, analytical method, and acceptance criteria](docs/product/DEEPWATER_PRODUCT_SCOPE_AND_ACCEPTANCE.md)
- [Target architecture and Mermaid workflows](docs/architecture/DEEPWATER_TARGET_ARCHITECTURE.md)
- [Current implementation ledger](STATUS.md)

The cross-product reusable idea is an explainable cycle: understand user intent,
analyze only permitted evidence, show the pattern and uncertainty, let the person
choose, then learn from explicit feedback. Each product must keep its own policies,
data, evaluation, and consent. It is not one universal recommendation score.

The repo currently contains a local proof of flow, not the target MVP. Use the
acceptance criteria as gates and the status ledger for verified implementation
facts. Do not claim Kafka, Azure Cosmos DB, vector search, moderation, or deployment
are complete until implemented and tested.
